6.5 Degradation & Fallback 上游会挂，你的系统该怎么办

难度 ★★☆ 阅读 ~14 min 面试出现频率 中高 前置 2.1 / 6.1
Core Concept 核心概念

四种失效模式，只有第一种会报错

把模型 API 当作一个依赖来做可靠性设计时，需要区分四种失效——它们的检测手段和应对方式完全不同，而只有第一种会以异常的形式告诉你：

失效模式表现检测应对
① 完全不可用5xx、连接失败容易——错误率飙升重试、切备用供应商、降级
② 限流429、配额耗尽容易，但常在流量高峰才暴露客户端限流、队列、优先级、多 key
③ 延迟劣化能用，但慢到不可接受中等——需要监控分位数超时 + 熔断，切勿无限等待
④ 质量劣化正常返回，答案变差最难——无任何异常信号质量监控 + 版本锁定（本章重点）

第④种是 LLM 系统独有的，也是最容易被忽略的。供应商更新了模型、调整了默认参数、或对某类内容加强了安全策略——你的代码没变、指标全绿，但输出行为已经改变了。这与 6.1 的主题一脉相承：凡是不会报错的故障，都必须被显式地观测。

降级阶梯：想清楚「退到哪里」

降级设计的核心不是「出错了怎么办」，而是「在完全正常和完全不可用之间，有哪些中间状态是可接受的」。把它想成一个阶梯，逐级下降：

三个必须做对的基础件

① 超时必须设，且要分层设。不设超时是最常见的错误——一个卡住的上游请求会占住连接、耗尽线程池，把局部故障放大成全站雪崩。流式场景要注意：需要同时设「首字超时」和「整体超时」，因为一个已经开始吐字但吐得极慢的请求，用单一的整体超时是抓不住的（2.1 的 TTFT/TPOT 分解在这里直接有用）。

② 重试必须带退避和抖动。固定间隔的重试会在上游恢复瞬间制造惊群，把刚缓过来的服务再次打垮。必须用指数退避 + 随机抖动。并且要区分该重试和不该重试的错误：429 和 5xx 可以重试；400（参数错误）、401（鉴权失败）、内容策略拒绝重试多少次都是一样的结果，只是在浪费配额和时间。

③ circuit breaker（熔断器）保护自己也保护上游。连续失败达到阈值后直接快速失败，不再发起请求，定期试探恢复。它的价值是双向的：既避免自己的线程被拖死，也给上游留出恢复空间——持续重试会阻碍对方恢复。

质量劣化：LLM 独有的那一类

前面三件是通用的分布式系统实践，而第④类失效需要 LLM 特有的应对：

① 锁定模型版本。凡是供应商提供带日期/版本后缀的模型标识，生产环境一律使用具体版本而非「latest」别名。别名会在你不知情时指向新模型。代价是需要主动跟进版本弃用通知，但这个代价远小于某天早上发现输出行为变了却找不到原因。

② 把模型版本记进 trace。这样质量波动才能与版本变更对齐（6.1）。没有这个字段，你永远无法证明「是他们改了」。

③ 用金丝雀集持续探测。准备一小组固定的输入（几十条即可），定时调用并比对输出。输出的结构性变化——长度分布突变、拒答率突变、格式合规率下降——是模型行为变化的早期信号。这比等用户投诉早得多，成本也极低。

④ 备用供应商要真的验证过。「我们有备用方案」如果从未在真实流量上验证过，那它在故障时大概率也不能用——不同供应商的 prompt 行为、格式遵循、拒答边界都不同，切过去可能引发一场新的事故。备用路径必须定期演练，哪怕只是每月切 1% 流量过去跑一天。

Case Study 公开 Postmortem

OpenAI 2024 年 12 月 11 日故障：一次遥测变更引发的全站不可用

公开事故复盘 · 依赖方视角的启示

事故经过（据其公开的事故报告）：2024 年 12 月 11 日太平洋时间 15:16 至 19:38，OpenAI 全部服务出现严重降级或完全不可用。起因不是安全事件，也不是新功能发布，而是一次向全集群推出新遥测服务的内部变更。

根因：新服务的配置无意中导致每个集群中的每个节点都去执行开销高昂的 Kubernetes API 操作，而这些操作的开销随集群规模增长。控制平面因此被压垮，引发级联故障。

为什么这个案例值得应用层工程师读——它不是「AI 特有」的故障，恰恰因此更有教育意义：

① 你的上游会挂，且时长以小时计。这不是理论风险。一个约四小时的窗口足以让没有降级方案的产品完整地经历一次「全站不可用」。把「上游 API 完全不可用 4 小时」写进你的设计假设，然后回答：这段时间里用户看到什么？

② 故障源常常在「无关紧要」的变更里。压垮系统的是遥测服务——一个用来提升可观测性的组件。这个反讽值得记住：基础设施类变更同样需要完整的灰度与回滚能力，不能因为「它不影响业务逻辑」就走快速通道。

③ 缓存会推迟症状，让归因变难。DNS 缓存在变更与故障之间制造了时间差。这是分布式系统的通用陷阱——「刚才那个变更没问题，都过了十分钟了」是一个危险的判断。

④ 最值得内化的一条：修复通道本身也可能被故障波及。on-call 工程师被锁在集群之外，无法执行 kubectl，这显著延长了恢复时间。对应到 LLM 应用上，这个模式很常见——如果你的降级开关、配置中心、或运维面板本身依赖着正在故障的那个组件，那么你会在最需要它的时候失去它。降级开关应当尽可能简单、独立、且可以在最小依赖下生效（例如一个静态配置文件或环境变量，而不是一个需要调用多个服务才能读到的动态配置）。

依赖方的行动清单：把上游 status page 接进监控；准备 L3/L4 级降级（只检索不生成、兜底回答）；演练降级开关而不只是实现它；确保降级路径不依赖可能同时故障的组件。

Tooling Sidebar 工具层
可靠性工具（会过期，正文不依赖本区块） 截至 2026-08

LLM 网关：LiteLLM、Portkey、Cloudflare AI Gateway 等提供统一接口、自动重试、多供应商回退、限流与缓存。它的主要价值是把回退逻辑从业务代码里抽出来，缺点是引入了一个新的单点——网关本身也需要高可用设计，否则你只是把故障点搬了个家。

弹性库：各语言的熔断/重试库（Python 的 tenacity、Java 的 Resilience4j 等）。不要手写重试逻辑——退避、抖动、错误分类、熔断状态机都有成熟实现，手写极易漏掉抖动或把不该重试的错误也重试了。

状态页监控：把各供应商的 status page 或其 API 接进自己的告警。知道「是他们挂了」而不是「我们挂了」能极大缩短排查时间——这是一条投入极低的信息通道。

批处理 API：对可容忍延迟的任务（离线分析、批量生成），使用各家的批处理接口通常有明显折扣，且不与在线流量争抢配额——这本身就是一种隔离设计，能防止批量任务把在线服务挤掉。

配额管理：了解你的限流维度（RPM / TPM / 并发数）并在客户端侧主动限流，不要等 429。同时按业务优先级分配配额——高优先级请求应该在配额紧张时优先通过，而不是先到先得。

Quiz 自测

章末自测

架构评审为一个 RAG 客服产品设计降级方案，假设上游模型 API 完全不可用 4 小时。用户在这段时间应该看到什么？

关键认识：RAG 系统不是一个整体，检索层和生成层会独立失效。模型挂了，你的向量库、BM25 索引、重排服务通常都还好好的。不要让整个产品陪着模型一起死。

按阶梯逐级设计：

L1 重试（秒级）：指数退避 + 抖动，只对 429/5xx 重试。

L2 切备用供应商（秒级）：切到另一家的同档模型。前提是这条路径定期演练过——不同供应商的格式遵循和拒答边界不同，未验证的备用路径在故障时很可能引发第二场事故。

L3 只检索不生成（这是最有价值的一级）：直接把召回的原文段落展示给用户，配上「AI 总结暂不可用，以下是相关文档原文」。信息是准确的、可溯源的，对相当一部分客服场景已经够用——用户本来要的就是那份文档。

L4 兜底回答：对高频问题走预置的静态答案库（这类问题本来就该有标准答案）。

L5 诚实失败 + 转人工：明确告知服务暂时不可用、给出预计恢复信息、提供人工客服入口。诚实地失败远好于给一个错误答案或一个 500 页面。

另外必须考虑的三件事：
① 降级开关本身不能依赖正在故障的组件——用静态配置或环境变量，别用一个需要调用多个服务才能读到的动态配置中心（这正是 OpenAI 那次故障中「工程师被锁在集群外」的教训）。
② 写操作要幂等——降级和重试期间可能产生重复请求。
③ 提前准备对外沟通话术，不要在故障时现写。

场景判断某天开始，用户反馈回答「变啰嗦了、而且经常拒绝回答」。你的代码一行没改。怎么排查？

这是典型的第④类失效——质量劣化，无任何异常信号。排查顺序：

① 查 trace 里的模型版本字段。如果用的是 latest 一类的别名，供应商可能已经把它指向了新模型。这是第一个该看的地方，也是为什么这个字段必须被记录——没有它，你连「是不是他们改了」都无法回答。

② 看输出的结构性指标时间序列。平均输出长度、拒答率、格式合规率、token 消耗。用户说的「啰嗦」和「拒绝回答」对应两个可量化的指标——确认它们是否在某个时间点发生了阶跃。阶跃点的时间是最重要的线索。

③ 跑金丝雀集。用那组固定输入调用，与历史记录的输出比对。这能在几分钟内确定「同样的输入，输出是否变了」——这是区分「模型变了」和「用户输入变了」的决定性证据。

④ 排除自己这一侧的变更。「代码一行没改」需要核实——检索索引是否重建过？知识库内容是否更新？prompt 模板是否通过配置中心被改过？「没改代码」不等于「没有变更」。

⑤ 查供应商的变更公告与 status page。模型更新、默认参数调整、安全策略加强都可能有公告。

确认是上游变更后的应对：
• 立即锁定到具体版本号（若旧版本仍可用），换取排查和适配的时间；
• 用 6.4 的回归集量化影响面，而不是凭感觉；
• 针对新模型的行为调整 prompt（拒答变多常常需要重新校准拒答的授权表述）；
• 把这次事件加进金丝雀集与回归集。

长期措施：生产环境永远不用 latest 别名；把模型版本、输出长度分布、拒答率做成常态监控。这类故障的检测能力必须提前建好，事后是补不回来的。

面试题改编「你怎么保证 LLM 应用的可用性？」

回答要先分类失效模式——这体现你知道 LLM 依赖与普通依赖的区别：

① 完全不可用（会报错）：超时 + 指数退避重试（带抖动，且区分可重试与不可重试的错误）+ 熔断器 + 多供应商回退。这些是通用的分布式系统实践。

② 限流：客户端主动限流（不要等 429）、按业务优先级分配配额、可延迟任务走批处理接口与在线流量隔离。

③ 延迟劣化：分层超时——流式场景要同时设首字超时和整体超时，因为一个吐字极慢的请求用单一整体超时抓不住。

④ 质量劣化（LLM 独有，也是最能体现水平的一点）：正常返回但行为变了。应对是锁定模型版本（生产绝不用 latest 别名）+ trace 记录版本 + 金丝雀集定时探测 + 输出结构性指标监控。

然后讲降级阶梯，重点是 L3：RAG 系统在模型不可用时检索层通常仍健康，可以只展示召回原文而不生成。这一级最能体现「把 LLM 应用看成可分层降级的系统」而非一个整体。

加分项：
• 降级路径必须演练——未验证的备用方案在故障时大概率也不能用。
• 降级开关不能依赖可能同时故障的组件（引用 OpenAI 2024-12-11 事故中「on-call 工程师被锁在集群外无法执行 kubectl」的教训）。
• 把上游 status page 接进自己的告警。
• 明确说出设计假设：「我们按上游完全不可用 4 小时来设计」——公开 postmortem 表明这个量级的故障是真实的，不是理论风险。
