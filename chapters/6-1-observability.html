6.1 Observability 可观测性：200 OK 不代表答对了

难度 ★★☆ 阅读 ~13 min 面试出现频率 中 前置 2.1 延迟指标
Core Concept 核心概念

传统监控在这里有一个致命盲区

传统服务的健康度可以用几个指标概括：错误率、延迟、饱和度。它们之所以有效，是因为「服务坏了」通常会以异常的形式表现出来——抛异常、返回 5xx、超时。

LLM 应用打破了这个前提。它最严重的故障形态是：HTTP 200、延迟正常、无任何异常日志，但答案是错的。模型不会因为不知道答案就报错，它会自信地编一个（3.1）。你的全部传统监控面板都是绿的，用户却在流失。

由此得出 LLM 可观测性的第一原则：质量必须被单独观测，它不会自己冒泡。如果你的监控体系里没有一个指标在回答「答得对不对」，那么你观测的只是「系统有没有在运行」，而不是「系统有没有在工作」。

三层指标，缺一不可

层次指标特点
① 系统层TTFT / TPOT 分位数、错误率、限流命中率、缓存命中率（2.2）可直接测量，与传统监控同构，但要按输入长度分桶
② 成本层每请求 token 数、单位成本、按功能/租户/模型分摊LLM 应用独有的一等公民指标——成本可以在一夜之间涨十倍而不触发任何告警
③ 质量层代理信号 + 抽样评估（见下）无法直接测量，只能间接推断，是本章的重点

成本为什么要单独成层？因为在传统服务里，成本与流量基本是线性关系，监控流量就够了。而 LLM 应用的成本可以在流量不变的情况下暴涨——某次 prompt 改动让缓存命中率归零、某个 agent 陷入循环多跑了 20 轮、检索召回数从 3 调到 20、用户开始上传超长文档。这些都不是「故障」，传统监控不会报警，但它们能让账单翻几倍。

质量层：用代理信号，而不是等用户投诉

质量无法直接测量，但可以用用户行为间接推断。这些信号的好处是零标注成本、实时、覆盖全量流量：

强信号（几乎确定出了问题）：用户重新生成、点踩、转人工、把同一个问题换个说法再问一遍。最后这个尤其有价值——它是「答案没用」的最诚实表达，而且用户不需要做任何额外动作。

弱信号（需要结合上下文判断）：会话中途放弃、响应后无任何后续动作、复制了答案但很快又提问。

结构性信号（可程序化判定，最可靠）：输出JSON 解析失败率、schema 校验失败率、工具调用失败率、RAG 场景下的「资料中未提及」拒答率、引用缺失率。这类信号不依赖用户行为，可以直接接进告警。

Tracing：一次请求横跨十几个环节

一次用户请求在 LLM 应用里可能展开成一棵 trace（调用链）：检索 → 重排 → 第一次模型调用 → 工具调用 → 第二次模型调用 → 输出校验。任何一环都可能是延迟或成本的元凶，而聚合指标看不见它们。

三个务必记录、却最常被遗漏的字段：① 模型版本——供应商静默更新模型时，这是你唯一能对齐时间线的依据（6.5）；② 缓存命中的 token 数——没有它就算不出真实成本，也发现不了缓存失效；③ prompt 模板版本——把 prompt 当作有版本的资产，质量波动才能与改动对齐。

关于记录 prompt 与响应原文：它对排查极其有价值，但也带来隐私与存储成本问题。务实做法是——脱敏后按比例采样存全量原文，失败案例存 100%，并设定明确的保留期限。不要因为「有隐私顾虑」就什么都不存，那会让整个系统变成黑盒；正确的做法是设计好脱敏与保留策略。

Case Study 案例

月底才发现的成本暴涨（匿名化）

一次 prompt 改动，把账单推高了数倍

背景：一个文档问答产品，稳定运行数月，成本曲线平滑可预测。团队有完整的传统监控——延迟、错误率、QPS 全部正常。

事件：某次迭代中，有人在 system prompt 的开头加了一行当前日期，用于让模型正确处理「最近」「今年」这类相对时间表述。功能测试全部通过，效果确实改善了，顺利上线。

后果：这一行改动让 prompt 前缀每天变化一次——更准确地说，让此前稳定的前缀不再稳定。prompt caching 的命中率从很高直接归零（2.2：匹配是从第 0 个 token 开始的精确前缀匹配）。每次调用都要为完整的 system prompt 全额付费。

0%
缓存命中率（改动前接近满命中）
正常
延迟、错误率、QPS —— 全部指标健康

从上线到发现的时间（靠月度账单）

为什么这么久才发现：因为没有任何一个指标在观测它。功能是对的、延迟略有上升但在正常波动范围内、错误率为零。唯一的信号是账单，而账单是月度的。这是一次典型的「监控盲区」事故——不是监控失灵，是压根没有对应的监控项。

修复与预防：
① 把日期移到 prompt 末尾（靠近用户提问），恢复前缀稳定性；
② 把缓存命中率做成一等监控指标并设告警阈值；
③ 把每请求平均成本做成日级监控，环比波动超阈值即告警——不要等月度账单；
④ 在发布检查清单里加一条：「本次改动是否触及 prompt 的前缀部分？」

可迁移的教训：LLM 应用有一类故障，其唯一症状是成本——功能正常、性能正常、用户无感。传统监控体系里没有为它准备的位置，必须显式地把成本做成一等指标，且观测粒度要细到「每请求成本」而不只是「总成本」（后者会被流量波动掩盖）。

说明：本案例为综合多个真实项目的匿名化复盘，不含任何可识别的公司、产品或个人信息。所述现象与修复为工程实践总结，非实验测量数据。
Tooling Sidebar 工具层
可观测性工具（会过期，正文不依赖本区块） 截至 2026-08

LLM 专用平台：Langfuse（开源，可自托管）、LangSmith、Braintrust、Arize Phoenix、Helicone 等，提供 trace 记录、成本核算、数据集与评估编排。核心价值是省掉自建 trace 存储与 UI，而不是它们的评估功能——评估仍然需要你自己定义指标。

OpenTelemetry：如果已有成熟的可观测性栈，用 OTel 的语义约定把 LLM 调用作为 span 接进现有系统，往往比引入一套独立平台更合适——LLM 调用只是你系统里的一环，把它割裂成单独的监控孤岛会让端到端排查更难。

成本归因：多数商业 API 支持在请求中带自定义标签/元数据，用于按功能、租户、环境分摊成本。从第一天就打上标签——事后想按业务线拆分成本，如果没打标签就只能重放日志。

告警设计要点：LLM 应用的指标噪声较大，固定阈值容易误报。优先用环比/同比变化率告警（如「每请求平均 token 数较过去 7 日基线上涨超过 30%」），而不是绝对值阈值。另外缓存命中率骤降是一个高价值的单点告警，它能覆盖本章案例那一整类问题。

Quiz 自测

章末自测

概念题为什么传统的「错误率 + 延迟 + 饱和度」监控体系，用在 LLM 应用上会留下致命盲区？

因为这套体系的前提是「故障会以异常的形式表现出来」，而 LLM 最严重的故障恰恰不会。

模型给出一个完全错误的答案时：HTTP 状态码是 200、延迟正常、无异常日志、无堆栈。从系统视角看，这次请求是完美成功的。模型不会因为不知道而报错——它被训练来产出最合理的下一个 token，而不是判断自己知不知道（3.1）。

还有第二个盲区：成本。传统服务的成本与流量基本线性相关，监控流量即可。而 LLM 应用的成本可以在流量完全不变的情况下暴涨——缓存失效、agent 多循环了几轮、召回数调大、用户开始传长文档。这些都不是故障，却能让账单翻几倍。

因此必须补两层：质量层（用户重试/点踩/转人工等代理信号 + 结构性信号如 JSON 解析失败率 + 抽样评估）和成本层（每请求成本、缓存命中率、按功能分摊）。缺了这两层，绿色的监控面板只能说明「服务在运行」，不能说明「服务在工作」。

场景判断用户投诉「最近回答质量下降了」，但所有监控指标正常。你按什么顺序排查？

第一步：先确认这是不是真的（并划定范围）。看代理信号的时间序列——重新生成率、点踩率、转人工率、同问题重问率。如果这些信号确实在某个时间点上升，就锁定了变更窗口；如果完全没有变化，可能是个别用户的主观感受或某个细分场景的问题，需要先定位人群。

第二步：对齐变更时间线。把信号上升的时间点与三类变更对齐——① 你自己的发布（prompt 模板版本、检索参数、模型配置）；② 供应商的模型版本变更（这就是为什么 trace 必须记录模型版本——静默更新是真实存在的，见 6.5）；③ 数据侧变更（知识库更新、索引重建）。

第三步：分桶定位。按查询类型、用户群、输入长度、检索命中情况分桶看指标。整体指标会把某一类的崩塌平均掉——常见情形是「某一类查询彻底坏了，但它只占 5% 流量」。

第四步：拿失败案例看原文。调出具体 trace，看召回的材料、完整 prompt、模型输出。这一步永远不能跳过——它能一眼区分是检索问题、prompt 问题还是模型问题（3.5 的归因矩阵）。

第五步：在 golden set 上复现。用固定评估集跑当前版本与上一版本对比，把主观的「感觉变差了」变成可量化的结论（6.4）。

如果排查完发现什么都没变——那么最可能的解释是用户的使用方式变了（新场景、新人群、新的提问方式），系统本身没退化，只是遇到了它没被设计来处理的输入。这同样是有价值的发现。

架构评审某团队的 LLM 监控方案：记录每次请求的耗时与是否报错，每月对账单做一次复盘。指出问题并给出最小可行的改进。

问题一：完全没有质量观测。这是最致命的缺陷——答错不报错，当前方案对最主要的故障形态完全失明。最小改进：先接三个几乎零成本的结构性信号——JSON/schema 校验失败率、工具调用失败率、拒答率，它们可程序化判定、可直接告警。再接用户侧的重新生成率与点踩率。

问题二：成本观测的粒度和频率都不对。月度对账单意味着一次成本事故最多可能持续一个月才被发现；而「总成本」会被流量波动掩盖。最小改进：做日级的每请求平均 token 数与平均成本监控，按环比变化率告警。再加一个缓存命中率指标——它单独就能覆盖一大类成本事故。

问题三：只有请求级耗时，没有 trace。知道「这个请求花了 3 秒」但不知道时间花在检索、重排还是哪次模型调用上，无法归因。最小改进：给每个环节加 span，至少记录耗时、输入/输出 token、模型版本。

问题四：没有记录版本信息。模型版本、prompt 模板版本、检索配置版本——缺了它们，质量波动无法与任何变更对齐，排查只能靠回忆。这一项改动成本极低但价值极高。

问题五：没有保留失败案例的原文。排查时无法复现。最小改进：脱敏后对失败案例存 100% 原文，成功案例按比例采样，设定保留期限。

按投入产出排序，如果只能做三件事：① 结构性质量信号 + 告警；② 日级每请求成本 + 缓存命中率；③ trace 中记录模型版本与 prompt 版本。这三件加起来大约几天工作量，却能覆盖绝大多数生产事故的发现与归因需求。
